## 기본 개념

### 프로세스 (Process)

OS가 실행 중인 프로그램에 할당하는 **독립적인 실행 단위**.

- 자신만의 메모리 공간(Code, Data, Heap, Stack 영역)을 통째로 가짐
- 다른 프로세스와 메모리를 공유하지 않음 → 하나가 죽어도 다른 프로세스에 영향 없는 격리(isolation) 보장
- 대신 프로세스끼리 데이터를 주고받으려면 IPC(파이프, 소켓, 공유 메모리 등)가 필요
- 생성·컨텍스트 스위칭 비용이 상대적으로 큼

### 스레드 (Thread)

프로세스 안에서 실행되는 **흐름의 단위**. 하나의 프로세스는 여러 스레드를 가질 수 있음.

- 같은 프로세스 안의 스레드끼리는 Code, Data, Heap 영역을 공유
- Stack(지역 변수)과 레지스터/프로그램 카운터는 스레드마다 독립 — 각자 다른 실행 흐름(어디를 실행 중인지, 어떤 지역 변수를 쓰는지)을 유지해야 하기 때문
- 메모리를 공유하는 만큼 생성 비용이 싸고 컨텍스트 스위칭도 가벼움
- 대신 같은 데이터에 여러 스레드가 동시에 접근하면 동기화 문제(race condition) 발생 가능

### 한눈에 비교

| 구분 | 프로세스 | 스레드 |
| --- | --- | --- |
| 메모리 공간 | 독립 (Code/Data/Heap/Stack 전부 별도) | Code/Data/Heap은 공유, Stack만 독립 |
| 격리 | O — 하나가 죽어도 다른 프로세스는 안전 | X — 하나가 죽으면 프로세스 전체가 종료될 수 있음 |
| 통신 방법 | IPC 필요 | 메모리 공유로 직접 가능 (대신 동기화 필요) |
| 생성 · 전환 비용 | 크다 | 작다 |

## 심화

### 컨텍스트 스위칭이 프로세스에서 더 비싼 이유

컨텍스트 스위칭은 CPU가 실행 대상을 바꿀 때, 현재 태스크의 상태(레지스터 값·프로그램 카운터·스택 포인터 등)를 PCB(프로세스) 또는 TCB(스레드)에 저장하고 다음 태스크의 상태를 복원하는 동작이다.

- **프로세스**: 메모리 주소 공간 자체가 다르므로 MMU의 페이지 테이블까지 교체해야 함 → TLB(주소 변환 캐시)가 flush되면서 캐시 미스가 늘어남 → 비용 큼
- **스레드**: 같은 프로세스 내에서는 주소 공간(Code/Data/Heap)을 그대로 유지 → Stack/레지스터만 교체하면 됨 → 비용 작음

### 동기화 문제 (Race Condition)

여러 스레드가 같은 공유 자원(Heap의 변수 등)에 동시에 접근·수정할 때, 실행 순서에 따라 결과가 달라지는 문제.

`count++` 는 한 줄처럼 보이지만 실제로는 **읽기 → 증가 → 쓰기** 세 단계다. 두 스레드가 이 세 단계를 겹쳐서 실행하면 한쪽의 증가분이 유실될 수 있다.

```java
// 동기화 없는 경우 — 결과가 1000000보다 작게 나올 수 있음
class Counter {
    int count = 0;
    void increment() {
        count++; // read → add → write, 원자적이지 않음
    }
}
```

해결책은 공유 자원에 접근하는 임계 영역(Critical Section)의 실행을 직렬화하는 것이다.

| 방법 | Java 예시 |
| --- | --- |
| 락(Lock/Mutex) | `synchronized`, `ReentrantLock` |
| 원자적 연산(Atomic) | `AtomicInteger` 등 `java.util.concurrent.atomic` |
| 세마포어 / 모니터 | `Semaphore`, 모니터 기반 락 |

```java
// synchronized로 임계 영역 보호
class Counter {
    int count = 0;
    synchronized void increment() {
        count++;
    }
}

// AtomicInteger로 락 없이 원자적으로 처리
class Counter {
    AtomicInteger count = new AtomicInteger(0);
    void increment() {
        count.incrementAndGet();
    }
}
```

### 멀티프로세스 vs 멀티스레드, 언제 뭘 쓰나

| 상황 | 선택 | 이유 |
| --- | --- | --- |
| 격리·안정성이 중요 (예: 크롬 브라우저 — 탭마다 프로세스 분리) | 멀티프로세스 | 하나가 죽어도 나머지에 영향 없음 |
| 가벼운 동시 작업, 잦은 자원 공유 (예: 웹 서버가 요청마다 스레드 할당) | 멀티스레드 | 생성·전환 비용이 작고 데이터 공유가 쉬움 |

트레이드오프: 멀티프로세스는 안전하지만 IPC 오버헤드와 메모리 사용량이 크고, 멀티스레드는 효율적이지만 동기화 버그(race condition, 데드락) 위험을 안고 간다.

## 헷갈리기 쉬운 포인트

- **데드락(Deadlock)**: 락을 잘못 쓰면 서로가 서로의 락을 기다리며 영원히 멈추는 상황이 생길 수 있음 — 별도 주제로 더 깊게 다룰 예정
- **스케줄링과의 관계**: 컨텍스트 스위칭이 언제, 어떤 기준으로 일어나는지는 CPU 스케줄링 알고리즘(Round Robin, CFS 등) 주제와 이어짐
- **Java의 스레드 vs 프로세스**: JVM 하나가 OS 프로세스 하나, 그 안의 `Thread`들은 OS 스레드에 매핑됨 (플랫폼 스레드 기준)

## 적용 사례

- **크롬 브라우저**: 탭/확장 프로그램마다 별도 프로세스로 실행 (멀티프로세스 아키텍처) → 탭 하나가 크래시 나도 브라우저 전체나 다른 탭은 영향받지 않음
- **웹 서버(WAS)**: 요청이 들어올 때마다 스레드 풀에서 스레드를 하나씩 할당해 처리 (멀티스레드) → 메모리를 공유하니 빠르지만, 공유 자원 접근 시 동기화 처리가 필요
